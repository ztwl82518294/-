| | 浏览型页面 | **档案型页面** |

### ★ 元信息：数据从哪来（关键调研结论）
用户要的「更新: 3天前 / 14次浏览」两个数据**项目里都不存在**，逐一查证：
- **时间字段：完全没有。** 实测 `E:\微信小程序公司信息\` 全部 475 条 → 0 命中时间类字段；`adminLine.pickFields` 的 `FIELD_WHITELIST` 也不含 `createTime`/`updateTime`。
  - **解法**：`_id` 是标准 ObjectId，**前 4 字节（前 8 位十六进制）= 创建时间秒**。这是唯一可靠且零成本的来源。
  - 三道校验（缺一不可）：① `_id` 必须 24 位十六进制；② 时间戳落在 2015~2100 合理区间；③ 相对时间**超 90 天返回空串**（不显示"286天前"）。
- **浏览量：能算但不划算。** `stat_events` 的 `view` 事件 `key` 存的是**线路 id**，要按公司聚合需 `where({type:'view', key: _.in(ids)})`；但 `stat_events` 只有 `month_openid`/`day_openid`/`month_type` 三个索引，**无 `type+key` 索引**，大数组 `_.in` 会退化为扫描，拖慢详情页。
  - **解法**：① 线路 id 上限 **30 个**（`VIEW_ID_LIMIT`），超出放弃统计返回 0；② **任何异常一律 try/catch 吞掉返回 0**，绝不影响主数据。

## 🎨 v6.2：全站移除毛玻璃（`backdrop-filter` 全删）

用户要求「**全部字体删除毛玻璃效果**」。用 AskUserQuestion 确认范围 → **「全部删（含管理端）」**。

### ★ 核心设计判断：只删模糊会变「更脏」
毛玻璃观感 = 半透明 + 模糊 + 饱和三者配合。**只删模糊、保留 `.88` 半透明**，卡片会变成"透着背景渐变的淡灰块"——比有模糊时更脏。
→ **必须同时把半透明白底提纯为实心白/近白**（`≥.95`/`.88+` → `#ffffff`；`.8+` → `rgba(255,255,255,.98)`；其余 → `rgba(255,255,255,.96)`）。

### ★★ 踩坑（脚本首版有 bug，已修复）：提纯误伤文字色
首版脚本无差别正则替换 `rgba(255,255,255,x)`，把 **`color: rgba(255,255,255,.96)` 也提纯成了近白**。
但这些是**深色渐变头图上刻意用的白色文字/占位符/图标**（搜索框输入文字、placeholder、清除按钮）。
提纯本身无害，**问题在于同时把它们的容器底改成了白** → 变成「白字白底」，文字直接消失。

**受影响并已人工修正的 5 处**：
| 文件 | 位置 | 修正 |
|---|---|---|
| `pages/index/index.wxss` | 首页搜索框 | input `#fff`→`#2b3a4d`；placeholder→`rgba(43,58,77,.5)`；清除按钮→浅灰底深灰字 |
| `pages/company-list/index.wxss` | 头部搜索框 + `me-btn` | 同上；`me-btn` 由白字改 `#2b6cb0` 蓝字 |
| `pages/line-query/index.wxss` | `fav-btn` | 白字改 `#2b6cb0` 蓝字；激活态由白改 `#eef4fb` |
| `pages/admin/ads/index.wxss` | 售位总览三统计 | 白字改 `#2c5f96`；分隔线改 `rgba(120,150,190,.28)`；`.is-empty` 卡底改 `rgba(246,248,251,.96)` |
| `pages/admin/ad-edit/index.wxss` | `hero-badge` 徽章 | 白字改 `#2c5f96` |

**脚本已修**：改为**逐行判定属性名**——只对「底色类」属性（`background*` / `border*` / `box-shadow`）提纯，**`color` 一律跳过**。
> **教训（已写入脚本注释 + PRD §8.3 + R-23）**：样式批处理脚本凡涉及"白色提纯"，**必须先按 CSS 属性名过滤**。白色既是背景色也是文字色，语义完全相反，无差别替换必炸。

## 🔧 v6.3：网点分组口径修复（用户报障 ★ 读端与写入端脱节）

用户报障原话：**「修改问题：电话不需要排序。发站电话对应发站电话，有多个发站地址，或者多个到站地址进行排序。」**
附截图（专线详情页发站/到站）：发站显示为「① 真实地址 + 053182518294 / ② 地址未填写 + 15165018553 / ③ 地址未填写 + 15508675779」，到站显示「① 真实地址 / ② 地址未填写」。

### ★ 根因定位（关键：数据没错，是渲染错）
先用 Node 复现，确认 **数据库里数据是干净的**：
```
parseOutlets(...) → [{addr:'真实地址', phone:'053182518294'}, {addr:'', phone:'15165018553'}, {addr:'', phone:'15508675779'}]
```
即 **1 个地址行 + 2 个纯电话行**（形态②字符串直灌）。但读端 `buildOutlets` **按行逐条成组** → 渲染成 3 个"网点"，其中 2 个没有地址。用户看到的就是"凭空多出几个没填地址的发站"。

**三个独立缺陷叠加**：
1. `splitPhones` / `splitAddrs` 各自 `.sort()` → 用户说的"**排序**"（打乱了运营录入顺序，第 1 个常是主号/主发货点）
2. `buildOutlets` 给每个孤立电话造一个"地址未填写"的空行 → 用户说的"**多个发站地址**"
3. 地址与电话解耦：地址卡不显示电话、电话卡不显示地址

### ★★ 与 PRD R-13 的冲突（规范与实现脱节）
R-13 第 2 条早有明文：「**单地址多电话保持 1 网点挂多号**（不按下标对位拆散成一堆"纯电话"组）」
—— 但这条**只在写入端**（`adminLine.deriveOutlets`）有护栏，**读端从未遵守**。
→ 已把 R-13 扩写为「**读端也必须遵守"单地址多电话 = 1 组"**」小节，含 4 种输入→分组结果对照表。

### 澄清（AskUserQuestion，三项全选推荐）
1. 展示方式 → **「合并：1 个地址卡挂全部电话」**
2. 「地址未填写」→ **「不再显示」**
3. 范围 → **「两个页面一起改」**（专线详情 + 公司详情）

### 统一分组规则（两处口径必须一致）
| 输入 | 分组结果 |
|---|---|
| 1 地址行 + N 纯电话行 | **1 组**：该地址挂 N 个号码 |
| M 个地址行（各带电话） | **M 组**：地址与电话严格一一对应 |
| M 个地址 + 尾随纯电话 | **M 组**：尾随号码并入**第一个**地址组 |
| 只有电话、没有地址 | **1 组**：`addr` 为空（前端**不再渲染**「地址未填写」） |

### 代码改动
**`pages/line-detail/index.js`**（核心）
- `splitPhones` / `splitAddrs`：**去掉 `.sort()`**，只保留去重 + 保持录入顺序
- `buildOutlets`：**整函数重写** —— 先分离 `withAddr` / `withoutAddr`，把无地址号码拍平并入第一个地址组；该侧完全无地址时合成唯一一组
- `data` 新增 `fromAddrCount` / `toAddrCount`；`loadLine` 用 `countAddr = ps => ps.filter(p => !!p.addr).length` 计算

**`pages/line-detail/index.wxml`**
- 发站/到站两个 `pf-st-item`：**删除** `pf-st-addr-empty`（「地址未填写」）分支
- 三统计：`fromPairs.length`/`toPairs.length` → **`fromAddrCount`/`toAddrCount`**；标签「发站网点/到站网点」→「**发站地址/到站地址**」

## 📝 v6.4：信息纠错改为站内表单（用户提供参考图）

用户提供两张参考图：图 1 是专线详情页的「信息有误？点这里报错」按钮，图 2 是要弹出的**修改页面**。
用户原话：**「请设计点击1图中'信息有误点这里报错'，弹出2图的修改页面。」**

### ★ 为什么必须改（旧实现的根本缺陷）
旧实现是 `showModal` 说明 → `showActionSheet` 二选一（打电话 / 复制微信）：
1. **用户必须跳出小程序、切到电话或微信 App** 才能完成反馈 —— 摩擦极大，实际几乎无人使用；
2. 反馈内容只存在于**客服的口头记录**里，没有结构化留存，**无法统计"哪家公司被反复报错"**。

→ 改为**站内表单**：`pages/report`，写完即提交，落 `feedback` 集合，后台集中核实。

### 页面结构（完全对照参考图）
① 「你要反馈的信息」琥珀提示条（对象名由路由参数带入，**为空整块不渲染**）
② 问题类型 chips 单选（电话有误/公司已停业/线路已取消/信息不完整/其他），**再点一次可取消**
③ 具体说明 textarea（必填，`maxlength=200`，右下角实时 `N/200`）
④ 上传凭证（选填，最多 3 张，虚线「+ 添加」，可预览/删除）
⑤ 联系方式 input（选填，`maxlength=60`）
⑥ 流程说明条「提交后我们会人工核实，核实通过后才会修改信息，不会立即生效。」
⑦ 固定底栏「提交反馈」（主色渐变；提交中置灰 + "提交中..."）

### 入口 3 处（原 2 处 + 新增 1 处）
1. 专线详情 `onReport` → `?kind=line&key=<lineRef>&name=<公司名>`
2. 公司详情 `onReport` → `?kind=company&key=<公司名>&name=<公司名>`
3. **「我的」菜单新增「信息纠错」** → 不带参进入（用于不在具体对象页时的反馈，如"某某公司已停业"）

> **传参纪律**：只用于提示条展示与写入定位字段，**不参与任何权限判断**；缺参不影响页面可用性。

### 新增云函数 `cloudfunctions/reportFeedback`（★ 必须上传）
`action:'submit'`，写入 `feedback` 集合。服务端五道护栏：
1. **类型白名单反查** —— 不信任前端 `typeLabel`（前端只传 `key`），用服务端映射表反查。
   理由：label 若被篡改会把任意字符串写进后台列表页，可能出现钓鱼文案。
2. **全部字段服务端再截断** —— 前端 `maxlength` 可被绕过，不兜住单条反馈能塞进几 MB 文本。
3. **频控** —— 同 openid 单日上限 **10 条**；计数失败时**保守放行**（宁多记勿漏记，与 `statLog` 同策略）。
4. **无 openid 直接拒**（`no-openid`）—— 不静默写成匿名反馈，否则后台既无法回查也无法频控。
5. **异常不抛穿** —— 失败返回 `{ok:false, reason, error}`，绝不返回 `undefined`。

集合字段：`{type, typeLabel, target, targetKey, targetKind, detail, images[], contact, status, month, day, ts, _openid}`
- `status` 初始 0（待处理），**云函数不改**，后台核实后自行改。
- `month`/`day` 按东八区，**与 `stat_events` 同口径**（便于同维度聚合）。
- `_openid` 服务端显式注入。

### 前端实现要点
- 选图 `wx.chooseMedia`（`sizeType: compressed`）→ `wx.cloud.uploadFile` 存 fileID。
- **逐张串行上传**：并发上传在弱网下失败原因难归因，且一次最多 3 张，串行耗时差异可忽略。
- **部分成功也保留**：已传成功的图不因后续一张失败而全丢。
- 删图时顺手 `cloud.deleteFile`，避免云存储留废图。
- **防重复提交**：`ui.lock(this,'submit')` + 按钮置灰。
- 云函数未部署时给 `ui.notDeployed('reportFeedback')` 可操作指引（避免用户误以为是网络问题反复重试）。
- `line-detail/index.js` 与 `company-detail/index.js` 的 `contact` 引入随之**删除**（旧流程才需要，已无引用）。
