## 意外收获：修好一个形同虚设的检查工具

清理中实跑 `check-requires.js`，发现它**长期报假失败**（把注释里的用法示例当真实依赖）：

```
❌ test\framework.js:12  ->  ../framework
```
（第 12 行是注释 `* 在套件里：const { ... } = require('../framework');`）

**假失败比不检查更糟** —— 会让人直接忽略整个检查。修复：加 `stripComments()`，
**剥注释但保留字符串**（`require` 的路径就在字符串里），且**用等长空白替换 → 行号不变**。

> 中途踩坑：第一版把字符串也抹掉了，输出变成「✅ 全部 **0 处** 相对 require 路径均有效」——
> 扫描形同虚设。**剥注释绝不能连字符串一起剥。**

修复后：`✅ 全部 64 处相对 require 路径均有效`，并**并入 `scripts/check-project.js`（8 类 → 10 类）**。

## 远程备份（第二件大事 · 已在本地就绪，等仓库地址）

仓库此前**无任何 remote，本机是唯一副本**（已上线，丢失代价高）。

### ★ 关键发现：GitHub 其实能连通
之前连续几轮都判定「沙箱代理拒绝 github:443（502）→ 推不上去」，**这个结论只对了一半**：

| 通道 | 结果 |
|---|---|
| 默认（沙箱代理 `127.0.0.1:59788`） | ❌ `CONNECT tunnel failed, response 502` |
| **仓库级 `http.proxy=http://127.0.0.1:7897`（Clash 类）** | ✅ **通** |
| Gitee（走沙箱默认通道） | ✅ 通（备选方案，最终未采用） |

⇒ 用户选了 GitHub 私有仓库。**下次遇到「GitHub 推不动」，先试给仓库单独配 `http.proxy=127.0.0.1:7897`，
不要直接下「推不了」的结论。**

### 为什么必须写成脚本（两处环境坑）
1. 本机 **Git Bash 的 PATH 已损坏**（`env` / `grep` / `ls` 全 `command not found`）→
   **无法用 `export https_proxy=...`** 传环境变量。改用**仓库级** `git config http.proxy`
   （不用 `--global`，免得影响其他仓库）。
2. **Node 的 `execSync` 在 Windows 上走 `cmd.exe` 而非 bash** →
   `git remote get-url origin 2>/dev/null || true` 会报「'true' 不是内部或外部命令」并**让整个脚本崩掉**。
   探测型调用一律用 `try/catch`（脚本里封装成 `trySh()`），**别写 POSIX 兜底语法**。
